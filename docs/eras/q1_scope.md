# q1_scope.md: hostile review of docs/eras/plan.md v1 (lens: SCOPE, SEQUENCING AND FEASIBILITY)

Reviewer lens: is the amount of work deliverable with the described orchestration (4 CPUs, workflows of 2 agents, one heavy job at a time)? What dominates the critical path? Which phase is built before its dependency? What hidden work is unnamed? Where does the plan shrink while claiming perfection?

Method: read e.md, plan.md, maps 01..07 (map 08 does not exist), then checked the plan against the repo. Numbers marked (measured) were produced by me with read-only probes on this box; numbers marked (est.) are my estimates and the assumptions are stated. Probes: all 93 non-slow test files timed one by one (336 s total, 0 failures, near idle box); the 36 stored campaign runs in `.cache/campaign` summed (536 battles, 78.0 CPU-minutes); `generateArena` golden hashes recomputed (marathon 69180a92, thermopylae 67e1ad1b, colosseum 6f4c0945 reproduce, so G2 is sound); `git log` span and commit shapes; grep counts for era coupling in `src`, `tools`, `tests`.

Ranking: BLOCKER (the plan cannot succeed as written), MAJOR, MINOR. 30 items.

## BLOCKERS

### Q1. BLOCKER. The plan has no capacity model: ten phases, zero durations, zero agent counts, zero token budget. Is it deliverable at all?
**Question.** What is the wall-clock, agent-session count and token envelope per phase on "2 agents per workflow, 4 CPUs", and what burn-rate triggers the cut ladder?
**Evidence.** plan.md section 13 lists phases P0..P9 with dependencies only. STATUS.md says "workflow cap 2 agents each". Previous project (git log, 50 commits): foundation commit 10-06 02:28 to verification report 17:56 = 15.5 h, with 18 named roles (docs/plan.md section B: 8 phase-1 agents, 7 phase-2 agents, plus COORD, AUDIO-HUNTER, ANIM spike) and a box at load average 10 to 15 (tools/balance.mjs:6). 10.5 h of those 15.5 h came AFTER the QA-round-1 fix commit (07:21): integration, retunes, humour pass, QA 2. Scale factors from the plan's own table: units 96 vs 43 (2.2x), arenas 36 vs 16 (2.3x), props 108 vs 41 (2.6x), missions 27 vs 9 (3x), music 18 vs 8 (2.3x), clips about 157 -> 280, plus 16 sim modules, 12 new rigs, render v2 and a registry refactor that touches 121 files (41 src, 2 generated, 13 tools, 65 tests). No telemetry on tokens exists anywhere in docs (grep).
**My estimate (est.; assumptions: average session 1 to 1.5 h, 4 to 6 agents effectively concurrent, i.e. 2 to 3 workflows).**
| phase | agent-sessions | wall-clock |
|---|---|---|
| P0 goldens + bibles + specs | 8 to 10 | 0.5 d |
| P1 foundation + 12 tracers | 45 to 60 | 2 to 3 d |
| P2 Medieval | 35 to 45 | 1.5 to 2 d |
| P3 Modern | 40 to 50 | 1.5 to 2 d |
| P4 Sci-Fi | 40 to 50 | 1.5 to 2 d |
| P5 integration | 15 to 20 | 1 d |
| P6 balance + campaign tuning | 20 to 25 | 1.5 to 2.5 d (box-bound) |
| P7+P8 QA x2 + fixes | 45 to 65 | 2 d |
| P9 report, publish, simulate user | 5 to 8 | 0.5 d |
Total 250 to 330 sessions, 6 to 12 days continuous, order of 150 to 400 M tokens (cached reads dominate). The plan states none of this, so nobody can tell on day 3 whether it is on track.
**Failure scenario.** Day 4: P1 is half done, the user asks for status, COORD cannot say whether 20% or 5% of the work is done; the cut ladder is never triggered because it has no trigger; the first cut happens implicitly (agents run out of context and hand back "PARTIAL").
**Required plan change.** Add a section "Capacity and schedule": per phase sessions, wall-clock, token envelope, owner; a calibration gate at the end of P1 (measure cost per tracer unit and per sim module, then re-estimate P2..P8 and write the numbers into STATUS.md); explicit triggers for each cut-ladder rung (e.g. "if P3 exceeds estimate by 30% after calibration, rung 2 is invoked and logged").

### Q4. BLOCKER. There is no merge or isolation strategy, and the repo rules forbid the tools that would provide one.
**Question.** How do ~22 roles avoid breaking each other's files in one working tree, when agents may not run git and COORD alone commits?
**Evidence.** docs/AGENTS.md: "Other agents are working in parallel in the same working tree", "Do NOT run `git commit`, `git push`, `git add`, `git checkout`, `git stash`". plan.md:155 "commits at every green gate". Previous project: 8 of 50 commits are "Agent work in progress" / "interim" / "working files" checkpoints because the tree was never green; docs/qa_round1.md:141 "did not run gate.mjs (it rebuilds dist/ under other agents)" and found `campaign/puzzles` red from in-flight edits; qa_round2.md:6 found `dist/` older than HEAD after a retune commit. `src/_generated/registry.*.js` are TRACKED files rewritten by every `tools/build.mjs` (gen-registry.mjs:28,52), and the fast gate runs build, so every agent's finish line writes shared tracked files and `dist/`. Hot shared files and their size: `anim/animator.js` 56 KB, `app/game.js` 54 KB, `sim/world.js` 52 KB, `app/meta.js` 48 KB, `audio/cues.js` 45 KB, `render/battleview.js` 28 KB, `ui/strings.js` 38 KB. **Required plan change.** State the isolation model: per-workstream git worktrees or branches (amend AGENTS.md so agents may commit to their own branch and COORD or an integrator agent merges), gate output directory per worktree (`dist/<agent>`), generated registry files untracked or regenerated only by the integrator, a file-ownership table for the 10 hottest files with a single editor each and a "patch request" path, and a merge queue order. Define "green" per branch, not per tree.

### Q5. BLOCKER. Golden G1 and non-negotiable 1 contradict the plan's own mechanics: M3 extends `stateHash`, and M10/M12/M14 fix bugs that change Ancient battle outcomes.
**Question.** How can G1 ("per-100-tick stateHash, asserted forever") stay green when `stateHash` itself is extended and when Ancient-visible bugs are fixed?
**Evidence.** world.js:899-905: `mix(v)` does `h ^= ...; h = imul(h, prime)` for every unit; mixing any new per-unit field, even zero, changes the hash of every Ancient battle. plan.md:9 ("`stateHash` is extended to cover the new state") and M3 (plan.md:72 "added to `Unit` ctor and `stateHash`"). Behaviour changes inside the plan: M10 "`_tickEffects` buffer aliasing fix" (plan.md:78); M12 "non-aoe projectiles hurt props via `structDmg`" (plan.md:80), which map 02 lists as "ballista bolts do no wall damage", an Ancient unit on Troy/Thermopylae walls, and G1 includes troy; M14 "`addPlacements` keeps `vip/general`, fixes `reachOnly` progress 0" (plan.md:82), which changes Ancient missions 2/3 behaviour; map 02 section 6 "Pre-existing bugs worth fixing in the same pass". **Failure scenario.** The first SIM agent that extends `stateHash` makes G1 red; the agent re-records the golden "because it is a hash", and the safety net is gone silently for the rest of the project (a re-record is indistinguishable from drift).
**Required plan change.** (1) G1 uses its own frozen copy of the hash function inside the test (position, hp, team, rng, tick as today), independent of `world.stateHash()`; production `stateHash` may grow. (2) Add a second golden, a per-battle result tuple (winner, tick of end, alive costs), so a legitimate extension cannot hide drift. (3) For every pre-existing bug fix, decide per bug: gated by a def/era flag (Ancient unchanged), or deliberately changed with a named, reviewed golden re-record entry in `docs/eras/cuts.md`-style log. (4) Rule: nobody re-records G1..G6 without COORD approval.

### Q6. BLOCKER. No sim-freeze milestone: balance, campaign records and QA fixes will keep invalidating each other; the fingerprint that detects this does not even look at the new eras.
**Question.** At what point is `src/sim` frozen so that balance and campaign records mean something, and what stops a QA-round fix in P7/P8 from invalidating all four eras' records?
**Evidence.** `tests/campaign/_lib.mjs` simHash (about line 152-159) hashes `src/sim`, `src/world` and `content/era_ancient/stats.js` ONLY; new eras' stats files are not hashed. `feasibility.test.mjs:47-51` prints STALE and SKIPS the replay on a fingerprint mismatch (it does not fail), so plan.md:59 "G6 ... `tests/campaign` fast tests stay green" is vacuous for the whole project; the puzzle replay (`puzzles.test.mjs`, 9.9 s measured) is the only real campaign drift check. W1 (the gencore split) also changes `src/world`, so simHash flips in P1. The balance run is scheduled in P6 (plan.md:152) after P2..P4 content, while sim modules M4..M11 land "in parallel with" P2 (plan.md:152), so Medieval is tuned on a sim that later changes under it. The Ancient project: QA round 2 fixes and a campaign retune (commit 15f50c0, 190 files) arrived after the dist build (qa_round2.md:6).
**Failure scenario.** Medieval is balanced in P6, then M9 (cover) and M12 (props as structures) land, then QA2 touches `combat.js`; every era's win-rate bands are stale and nobody knows because the replay test skips. The final report claims bands that were measured on a different sim.
**Required plan change.** (1) Add "S-FREEZE": all 16 modules merged and Ancient goldens green before any era balance or campaign record is taken; after S-FREEZE, a sim change requires COORD approval and a named re-record of all affected eras. (2) Make simHash per era (sim + world + that era's stats) and make a stale record FAIL the full gate, not skip. (3) Record per-mission fingerprints that include the units the mission uses, so only affected missions re-run. (4) QA fixes after S-FREEZE that touch `src/sim` go to a batched "sim fix window" followed by one re-record.

### Q8. MAJOR. The heavy-job queue (balance, feasibility, mirror, fuzz, modes, gate) is the real wall-clock of P6 and nobody has added it up.
**Question.** How long does one full measurement pass over three new eras take under one heavy lock, how many passes are expected, and what runs concurrently with agents' own gates?
**Evidence.** Stored Ancient campaign runs (measured): 36 files, 536 battles, 78.0 CPU-minutes, 8.7 s per battle; tools/balance.mjs:6-9: full run "47 min on a box with a load average of 10-15, about 25 min on an idle one" for 43 units / 15 arenas (pairs 3-6, mirror 21-23, fuzz 6-8), `tune` 8-11 min per round, `feasibility.slow` about 10 min. Scaling (est.): 27 missions x 50 battles = 1,350 battles = 3.3 CPU-h = about 50 min wall on 4 exclusive cores, 1.7 h if new-era battles (vehicles, air, shields) are 2x heavier; balance per era 15 to 20 min idle (32 units, 12 arenas), 30 to 40 loaded; the S22 mirror alone is 12 arenas x 400 battles x 3 eras. Passes needed: at least 3 per era (first measure, after tuning, after S-FREEZE) plus a re-run after each QA sim fix window: (est.) 6 to 10 h of exclusively locked box time for balance and 4 to 6 h for campaign records, during which agents' own gates (about 7 to 8 min idle, see Q14) compete for the same 4 cores. Contention is not hypothetical: `ui/x2_a11y` takes 18 s idle (measured) and timed out at 280 s under the previous multi-agent load (qa_round1.md:141), more than 15x.
**Failure scenario.** The lock queue grows during P2..P4 (agents want gates, balance wants the box), balance slips to the end, and P6 (est. 1.5 to 2.5 d) becomes 4 d; or agents skip the lock because their hand-back needs a gate, and the numbers are taken under load with timeouts.
**Required plan change.** Add a "heavy-job budget" table: jobs, CPU-minutes, frequency, queue order; dedicate windows (e.g. nights/"quiet hours" in which no agent runs gates); incremental records (Q6); run-to-completion priorities; and say that gates by agents use `nice` and a worker cap. Reserve the box (no agent gates) for balance windows.

- Safety nets first (G1..G6) and the `rng2`/second-stream rule; G2's 16 hashes reproduce exactly (checked three); only the G1 hash function needs decoupling (Q5).
- Era as pack + registry with a throwing `mergeKind`; Ancient ids never move; tombstones before anyone moves an id.

## Verdict

Converged: NO. Product ambition and architecture (registry, packs, goldens, contracts) are sound, but the plan is not yet a schedule: it has no durations, agent counts or token envelope (Q1), its critical path is a serial 16-module SIM chain in a shared tree with no merge model (Q2, Q4), the tracer rule and the phase order contradict the mechanic order (Q3, Q7), the central safety net (G1) is invalidated by the plan's own changes (Q5), nothing freezes the sim before balance and campaign records (Q6), and the target numbers sit below Ancient parity and below e.md's own D4 while the title says "no MVP" (Q11). Seven BLOCKERs must be answered with concrete plan changes (a WBS with phases and owners, a schedule with a calibration gate, an isolation/merge model, a decoupled G1, an S-FREEZE milestone, a tracer era) before spec.md is written.
