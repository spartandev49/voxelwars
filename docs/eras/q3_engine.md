## PLAN BLOCKERS

### B1. Node-vs-Chromium `stateHashFull` parity (ER13), the "doc states which regime the shipped game matches" claim (AR6) and the provenance fallback (section 3) cannot hold: the same code diverges between engines

**Question.** Can a Node run and a Chromium run of the same build, seed and defs produce identical `stateHash(Full)`, as ER13 requires and as the provenance fallback ("require digests identical to the Node run of the candidate") assumes?

**Evidence.** Probe 1 (scratchpad `q3math.mjs`, `q3math2.mjs`): the same 20,000 deterministic inputs through `Math.sin`, `Math.cos`, `Math.pow`, `Math.acos` give different doubles in Node v22.22.0 and Chromium 141 (the repo's `/opt/pw-browsers/chromium-1194`): sin differs on 634 of 19,999 inputs, cos on 660, pow on 2,002 (max relative error 2.2e-16, i.e. 1 ulp); `atan2`, `hypot`, `sqrt`, `exp`, `log`, `tan` matched. The sim uses `Math.sin/cos/pow` in `ai.js` (2), `combat.js` (4), `projectiles.js` (3), `formations.js`, `squads.js`, `possession.js`, `world.js`, `stats.js` (cost) and `armygen.js`. Probe 2 (`q3entry.mjs`, `q3run.mjs`): the unmodified Ancient build (esbuild IIFE of `tools/lib/harness.mjs` `buildWorld`, marathon/medium, 60+25+25+12+10+2 per side, same DEFAULT_META regime in both engines, seeds 1, 2, 3) is bit-identical in both engines at ticks 100, 400 and 900, and DIVERGES for all three seeds by tick 2500 (seeds 1 and 3 already differ at tick 1500, e.g. seed 1 Node 101310472 vs Chromium 848760509; seed 2 is identical at 1500 and differs at 2500; end-of-battle hashes differ in all 3 seeds, e.g. seed 1 Node 313287398 vs Chromium 2255452573). Chromium run twice is identical to itself (probe `q3run2.mjs`), so the divergence is the engine, not nondeterminism. This is independent of the clip timing regime of AR6: both runs used the same one. The user's own browser is a third engine version.

**Required plan change.** (1) ER13 and section 3: replace "Node-vs-Chromium `stateHashFull` parity" by three comparator classes: (a) bit equality only WITHIN one engine (Node vs Node, Chromium vs Chromium, baseline-build vs candidate-build run in the SAME engine); (b) cross-engine: report the first-divergence tick (900 to 2,500 ticks in the probe for 300-unit battles) and require the AR6 statistical bound (200 battles: win-rate within 3 points, median end tick within 2%); (c) outcome-critical stored artefacts (campaign `reference` armies, puzzle solutions, star thresholds) must win with margin in BOTH engines. (2) Provenance fallback: the hosted fragment run in Chromium is compared with the candidate build run in the same Chromium, not with Node digests. (3) AR6 "the doc states which regime the shipped game matches" is amended to state also that no Node record is bit-comparable to the shipped game after about 1,000 ticks and that G1/G6 are Node-engine records. (4) ER8: the `campaign_play` replay-equality assertion compares Chromium record to Chromium replay (record taken in Chromium).

### B2. The landing-order table puts M15 and M17e last (#18, #19) while E-FREEZE(Medieval) requires them and Modern/Sci-Fi E-FREEZE do not mention them

**Question.** With "SIM, one agent at a time" and a table titled "Landing order = true dependencies", when can P3 for Medieval start?

**Evidence.** Section 4: E-FREEZE(Medieval) = "through #11 + M15 + M17e"; the table gives M15 = #18 and M17e = #19, "needed by: all". Read literally, the SIM agent lands #12 M8 .. #17 M6b first, so Medieval's E-FREEZE happens after Sci-Fi's mechanics, i.e. at S-FREEZE; the Medieval mechanic slice ("after #11") can still run, but "P3 for an era starts at its E-FREEZE" and the overlapped per-era pipeline (section 12: Medieval content/balance while Modern/Sci-Fi mechanics land) collapse. E-FREEZE(Modern) "through #14" and E-FREEZE(Sci-Fi) "through #17" omit M15/M17e although both eras need them, so the three definitions are not the same kind of set. Code check that M15 and M17e need nothing from #12..#17: M15 (barks, lessons, waves, god-power schema, `env.gravity` multiplier) touches `sim_text`, `lessons.js`, `waves.js`, `godpowers.js`, `projectiles.js` gravity (M2), and M17e needs M1 (causes), M12 (wreck props, `spawnProp` exists at `abilities/throne.js:17`) only. Also section 12 P1 lists "M15a plumbing" which is not a row of the table.

**Required plan change.** Reorder the table: M15 -> #12, M17e -> #13 (S ids stay attached to their modules: S45 M15, S46 M17e; the S ids need not be monotonic in landing order), then M8 #14, M9 #15, M11 #16, M4 #17, M5 #18, M6b #19. Define E-FREEZE uniformly as a prefix: Medieval = #1..#13; Modern = #1..#16; Sci-Fi = #1..#19 (= S-FREEZE). Update every number that quotes the old positions: mechanic slices ("after #11/#14/#17" become #11, #16, #19 or are restated by module name), "SIM #6-#19", calibration checkpoint 2 (M7 + M12 + M14 are #8, #9, #10: unchanged), and replace "M15a plumbing" by "M15 (plumbing part) in P1, remainder at #12" or delete the split.
