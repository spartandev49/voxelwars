## 1. CONTRADICTIONS AND CONTRACT GAPS

**C2-1. hum1 is 29 voxels tall, not 25.**
Where: spec.md §1 "(a 25-voxel soldier is 2.5 u tall)" and §3.1 "Standing height without crest ≈ 25 voxels = 2.5 u" vs the §3.1 table: legs 5+5 (feet at y 0, hip at 10), body origin y 10 + 9 tall = 19, head origin +9 = 19, head 10 tall = **29**; crest (origin 6 on head, 8 tall) reaches **33**. U2 requires "height 2.2-2.9 u", so every crested helmet (hoplite, spartan, centurion, strategos...) fails U2 as written.
Wins: the table (it is what the builders and tools/anim build against). Change §1/§3.1 text to 2.9 u (3.3 u with crest) and U2 to "2.4-3.4 u incl. crest".

**C2-2. hum1 `back` part is geometrically wrong.**
Where: spec.md §3.1 `back | body | 12,14,8 | pivot 6,7,0 | origin 0,7,-2.5`. Vertices are placed at `(voxel - pivot)*size`, so pivot z=0 means the whole 8-deep grid lies on +Z = forward of the pivot. The pivot sits on the torso's back surface (z -2.5), so quivers/wings/banner poles/backpacks grow through the torso and out of the chest. Pivot z must be 8 (content extends toward -Z). Add the same sanity rule for every part: a "which side of the pivot does the grid extend" table.

**C2-3. Weapon and shield dimensions contradict ground, range and the Workshop caps; orientation conventions are unstated.**
Where: §3.1 `offhand up to 20,22,10 pivot 10,11,5 origin 0,-4,0.5`, `weapon up to 9,48,9 pivot 4,10,4`; editors.md §2 "weapon reach <= 3.6 u"; units.md hoplite `range 2.0`.
(a) Forearm hand point is at root y 9; a 22-tall offhand centred there bottoms out at y **-2**: a full hoplon hangs 0.2 u into the terrain at idle. (b) The weapon extends 38 voxels = 3.8 u above the grip, beyond the Workshop's own 3.6 u limit, while the sim range is 2.0 u: a spear in thrust pose pokes 2+ u through the victim. (c) Nothing says which grid axis is the blade/shaft direction or the shield face normal at rest; the existing skin demo had to hack `origin x 2.5` and `rest [0, pi/2, 0]` on its shield to look right. Add: conventions (weapons authored pointing +Y with the edge facing +Z, shields face +Z), max offhand 16x18, and a rule tying visual length to `melee.range` (range is authoritative; compileSoldier clamps the weapon so tip distance = range - radius + 0.3).

**C2-4. Part ids violate the project's own id rule; cape2 exists only in a parenthesis.**
Where: spec.md §0.8 "Every id (unit, prop, part, clip, ...) is lower_snake_case" vs `armUL`, `legLL`, `legFL`. tools/anim/retarget.mjs, mapping_ual.json and the skin demo already use camelCase. `cape2` is mentioned only inside the `cape` row; plan §2 says "11 body parts" where the table has 10. Winner: amend §0.8 ("part ids are exempt and fixed by §3.1") because three tools already depend on the camelCase names; list all 16 parts in the table. Also state that `armLL` = arm Lower Left (the abbreviation is ambiguous with "arm Left Lower").

**C2-5. The 24-part cap is arbitrary and the roster already breaks it.**
Where: spec.md §3 "At most 24 parts per model (render texture limit)"; voxskin.js throws at P > 24.
There is no texture limit: the part texture is `3*P` texels wide; WebGL2 guarantees 2048. A mounted humanoid is 8 (quad1) + 16 (hum1) = 24 exactly with zero spare parts for ears, mane, barding, saddle. Chariot archer (2 horses = 16 + chariot + 2 wheels + archer 16 + driver) = 35+; war elephant with two animated howdah archers = 25+16*2; catapult "3 crew figures animate cranking" = 3x16 + frame; ballista crew of 2 similar. Wins: raise the cap to 48 (texture 144 wide, CPU cost only matters for the few bespoke units), define `hum_lite` (body, head, 2 arms, legs = 6 parts) for crews and spectators, and allow attached sub-instances for anything bigger.

**C2-6. Clip contract is under-specified and already disagrees with the code that exists.**
Where: spec.md §6 vs src/anim/clips.js and tools/anim/retarget.mjs.
- Spec: `ClipLib: get, duration(id), meta(id)`, sim reads `ClipLib.meta(clip).hitFrame/30`. Code: `dur(id)`, `meta(id)` returns `{dur, hit, loop, speedRef}` **in seconds**, plus `hit()`, `ids()`, `register()`. A sim written to the spec breaks. Code wins; rewrite §6.
- `parts:{id: Int16Array/Float32Array [rx,ry,rz per frame]}`: Int16 needs a scale (not given), interleaved vs per-axis not given; the retarget tool emits JSON arrays rounded to 3 decimals.
- Clips carry only rotations (+rootY/X/Z/pitch) while the pose is 9 floats per part and plan §2/e.md promise anticipation, overshoot, squash and stretch. Squash/stretch and weapon overshoot need per-part translation and scale tracks (optional fields).
- "Weapon/offhand tracks come from per-style authored overlays": no format.
- `u.anim` carries ONE clip, but mounted units need a mount clip and a rider clip at once (gallop + lance thrust). Add `u.anim.mount`. No rider clip exists in the min set (`ride_idle`, `ride_strike`, `ride_shoot`).
- Who maps unit state to clip id (hit_front vs hit_back vs stagger vs death_*)? The sim, per §6, yet it is unspecified and it determines kill-cam, debris and gag timing.

**C2-7. VoxSkin spec §8 does not match voxskin.js.**
Spec: `skin.add(worldMat4, pose, teamRGB, flash, extra?:{dissolve})`, `new VoxSkin(engine, modelDef, ...)`. Code: `add(x,y,z,h,sx,sy,sz,pose,team,flash,stone,glow,pitch,roll)` and a `host` with `.scene`. `dissolve` does not exist; `aFx.w` is "reserved". Per-instance visual states the spec requires have no slot: burning, tipsy/wine, frozen, selected, outline, low-hp, "stoned" is the only one (code). Attach convention differs: `ModelDef.attach` stores voxel coords inside the part grid, `VoxSkin.attachWorld` expects world units relative to the pivot. The sim cannot call either (no animator import) yet projectile launch points ("muzzle") are a sim concern: say how the sim derives them (def-based offset) and that `attachWorld` is FX-only. Code wins for the signature; spec gets the status params.

**C2-8. Unit identity and corpses are undefined.**
Where: spec.md §7 "`world.units` dense array of live Unit objects (stable object identity; dead units are recycled)" vs "Unit fields read by render: ... `alive` ..." and plan §2 "corpse policy (N bodies then sink/fade)" and A7 "death clip then burst into debris".
Dead units are removed and recycled, yet a dying unit must keep rendering for 1-1.4 s (death clip) and corpses persist. Events carry numeric ids (`unit_kill {src,dst}`, `kill_streak {id}`, `chicken_tantrum {id}`) that consumers (announcer chains, kill feed, achievements) hold across frames: with recycling, a stale id points at a different soldier. Add: `id` = monotonically increasing (never reused) with a generation or a Map; `world.corpses` ring (pure data: def, team, pose snapshot, clip, t) owned by sim; `px/py/pz` reset on spawn to avoid interpolation streaks.

## 2. FEASIBILITY RED FLAGS

**F2-2. Geometry cost: the mesher cannot hit PF2.**

Needed: per-type LOD meshes (2x voxel downsample by majority vote, ~25% quads; ~250 lines in voxel/ + VoxSkin holding near/far InstancedMesh pairs = 2 draw calls per type); the shadow pass uses the far mesh; greedy merge only where no AO/jitter matters (spear shafts, shield faces are the heaviest per voxel: a 36-voxel spear = 144 quads). Then set tier caps: Marble 300 near + 200 far. Re-derive PF2/R2 from this table.

**F2-3. Roster production is the real critical path and one agent cannot hold it.**
25 humanoid blueprints need >= 70 part builders (helms >= 22, faces, torsos 12, weapons >= 27, offhands >= 9, backs, capes), ~2k lines, each judged at three zoom levels; 18 mounted/bespoke models at 150-400 lines each (elephant ~300, chariot ~350, catapult ~250); 43 units x 3 zoom contact sheets. About 6-8k lines of modelling code and 130-200 rendered sheets at 3 iterations. Substitute: split UNITS into two agents by faction group (shared parts library owned by one), freeze the parts library before blueprints, and make the per-unit Definition of Done a CI-checked JSON (silhouette sheet path, clips present, text complete).

**F2-4. COORD owns ~18-20k lines and every gate.**
Sim core + AI layers + combat + 29 ability behaviours + objectives + god powers + armygen + waves ~9-10k; render (VoxSkin exists; post ~200, props ~600, FX ~1.2k, cameras ~900, preview service ~300) ~4k; save/share/deflate fallback/migrations ~1.2k; app (state machine, input, perf, diagnostics, boot, loop) ~3k; plus build, registry, lint, gate, integration, publishing. Substitute: a SIM agent (world/ai/combat/abilities/objectives/godpowers + their tests and the balance harness) behind the frozen §7 contract; COORD keeps render, app, save, gates.

**F2-5. T1 is three tiers wide.**
T1 = 43 units, 14-16 arenas with props and staged destruction, all abilities and god powers, camera modes, juice, HUD, announcers, survival, 9-mission campaign, codex, achievements, stats, settings, credits, in-house post. That is ~75% of the game behind one gate and one publish. Split: T1a (roster, arenas, HUD, juice, announcers, quick battle complete) / T1b (campaign, survival, codex, achievements, stats, credits), each with its own publish and a written cut order inside it (R2-17).

**F2-6. Editors.**
Arena Builder (15 tools, 12-brush falloff/shape options, symmetry, validators with Fix buttons, delta undo, library with thumbnails, playtest handoff) ~3.5k lines; Workshop (>= 18 helms, >= 18 main hands, stats, abilities, personality, roster, 3D turntable with clips) ~3k; Voxel Painter (3D face-pick painting + 2D slice, 12 tools, palette, mirror, undo, touch, onion skin) ~3k; plus Playwright pointer-sequence tests for all three. ~10k lines for one agent and T2. Substitute: two agents (Builder; Workshop+Painter) and share one undo/command library.

**F2-7. Balance and fuzz runtimes.**
4 cores here. At ~1.5 ms/tick a 150v150 battle (2,700 ticks) is ~4 s. U5 (43x42/2 pairs x 10 seeds, equal-cost mass battles) = ~9,000 battles = ~10 h single core, 2.5 h on 4 cores. S11 (2,000 termination fuzz, worst case 10,800 ticks each) ~0.6-3 h. S22 at n >= 400 x 14 arenas x 2 sides = 11,200 battles = ~3.5 h on 4 cores. U8 (5,000 blueprints). Run 20v20 for pair matrices (~0.5 s), 150v150 only for S22/perf, and put the runtime budget in verification.md or the harness will be the first thing dropped.

**F2-8. Audio production is ~340 files, curated blind.**
audio.md lists ~113 cue families x >= 3 variants = ~340 MP3s, each with a ledger row (author, URL, licence, edit notes), plus 6-8 music tracks with loop validation. Nobody can listen. Real risk is wrong-category picks (an "elephant_trumpet" that is a trombone). Substitute: ~60 families at >= 3 variants (combat, UI, death, horns, crowd, siege, thunder), the rest 1-2 variants plus pitch jitter; automated checks (duration, spectral centroid class, loudness) per category; state in the final message that audibility/appropriateness is unverified.

**F2-9. Copy volume.**
43 units x 8 text fields = 344, + 90 announcer lines, 40 tips, 24 achievements (48 strings), 9 missions x ~12 strings = ~110, 60 epithets, kill verbs, settings jokes, name parts: ~800 shipped strings, ~1,100 drafted to survive a 30% cut. One HUMOR agent grading its own lines is not an editor (R2-9).

**F2-10. Verification reading volume.**
344 unit-clip filmstrips (43 x 8), 48 arena camera shots, ~20 screens x 4 viewports = 80, weather/time sheets: ~500 images read by a model at ~1.5k tokens each is ~0.75 M tokens per full pass, repeated each gate. Fine once; not per merge. Use golden-image diffs (M-class) per merge and full reads at gates only; budget it.

## 3. REMAINING DEFICIENCIES FOR A CLOSEST-TO-PERFECT RESULT

**R2-1. Losing teaches nothing.**
Pill: The player loses to cavalry for the fifth time and the results screen shows kills and an MVP. The counter system (brace, charge, shield arcs, friendly fire) is the game's depth, and v2 only makes it visible during the fight.
Demand: results tablet shows 3 generated "lessons" from the event log (e.g. "14 of your archers died in melee after 2 cavalry charges", "your spear block never braced: units were moving", "your elephant panicked at 3 fire hits", "friendly fire cost you 9 units"), each with a one-line fix and Cassandra voicing it ("I said so"). Event data already exists (`charge_hit`, `unit_brace`, `friendly_fire`, `army_low`); add a pure `lessons.js` and tests.

**R2-2. Placement has no advice.**
Pill: Counter-picking is the entire placement puzzle, yet the player must read the Codex to learn it. Round-1 Q46 added hints; nothing shows composition weaknesses before pressing FIGHT.
Demand: a "Scout report" strip in placement (cavalry present with no spears, no anti-siege, exposed archers, budget share per role, enemy composition style when known) built from the armygen counter tables; per-card counter chips; optional Cassandra pre-battle warning. Tested against S20's counter style.

**R2-3. Replay and a real kill-cam were deferred, but the sim already makes them cheap.**
Pill: Plan §3 defers full-battle replay "because cross-browser determinism"; replay is same-browser by definition and S1 promises exactly that. Kill-cam is "kept" but undefined (C2-26). Instant replay of the winning moment is the most shareable thing this genre produces.
Demand: record (setup, seed, tick-stamped inputs) (C2-13), keep a state keyframe every ~10 s of sim (a flat typed-array copy of unit fields, designed now), replay by re-simulating from the nearest keyframe at 0.25-4x with free camera; kill-cam = last 4 s before a hero/boss/streak kill. Budget: seek <= 1 s. Make Replay a results-screen button.

**R2-4. Nothing measures "fun".**
Pill: S12 measures battle length; the harness could pass a game whose every battle is a 70 s steamroll with no lead change.
Demand: harness fun metrics per default setup over 200 battles: lead changes per battle (>= 1 in >= 40% of battles), comeback rate, steamroll rate (winner keeps > 80% of cost) <= 20%, close-finish rate >= 25%, gag-event rate per battle (>= 1 in >= 60% of "chaos" battles), kills/s variance (no 60 s dead air), announcer lines per battle (8-15). Put thresholds in verification.md and report distributions, not means.

**R2-5. "Cannot report back" is false; the biggest verification gap has a cheap fix.**
Pill: Every honest-limitation row (real GPU frame rate, CSP behaviour, audibility proxies, wrapper quirks, load times) is "H" because plan §0 says the hosted page cannot talk to the builder. The `db` capability lets the page write documents that Claude reads with `ArtifactData`.
Demand: a Diagnostics beacon (opt-out toggle in Settings > Data, default on for the owner): on first load and on any error, write one doc `diag/<random id>` with WebGL renderer/GPU strings, tier, measured frame time p50/p95 over 10 s of the title diorama, time-to-title, `securitypolicyviolation` events, audio load paths (embedded/fetched/synth/failed), storage status, codec support, error stack, build id. Rate-limited, size-capped, no PII, no secrets. Declare `db`; verify with one probe publish that declaring it does not break public sharing the user expects (if it does, ship a second "diagnostic build" link for the user). This converts several `H` rows into measured rows after the first user visit.

**R2-6. Sharing is a paste of up to 60k characters.**
Pill: M8: most chats reject it; the artifact sandbox blocks `<a download>` but offers `downloads.save`, and file inputs/drag-drop with `FileReader` work (M9). The soldier code is fine (small); the arena code is the one friends will actually want.
Demand: three channels with one parser: short text code for soldiers/armies (<= 1.8 KB when unpainted, size class shown), `.vwarena`/`.vwsoldier` file via `downloads.save` + file input/drag-drop import, and PNG export (photo mode, results card) via `downloads.save`. Palette-indexed binary payload with varints (C2-27). Declare `downloads`. Round-trip fuzz on all three channels.

**R2-7. The two most-seen animations are underspecified: death (300 per battle) and the swing/impact.**
Pill: A. All deaths use three clips and a debris burst; by battle three they are wallpaper. B. FX spec §8 lists debris, particles, projectile trails, decals, numbers, bubbles. e.md promised smear arcs; there are no melee swing smears, impact sparks per material (flesh, bronze, wood, stone, shield), dust on charge, footstep dust, banner cloth, or hit-direction flinch variants.
Demand: a death matrix (cause x direction x overkill x size -> 8+ behaviours: flung with pitch/roll tumble, crumple, spin, run-flailing on fire, stone shatter, sink in lava, comic puff for chickens), plus shield/helmet detaching as separate debris on death; an FX inventory with budgets for swing smears (instanced ribbon), sparks per material, dust, and who triggers them from which event.

**R2-8. 90 announcer lines are a 3-hour supply at one line per 8 seconds.**
Pill: Round-1 Q62's answer (recency memory, 5-minute repeat < 8%) measures the wrong horizon. At ~10 lines per battle and 20 battles per evening, every line is heard ~2 times per evening; by the third session the announcer is furniture. Plus the best humor system in the genre is memory.
Demand: persistent callbacks via `vw.progress`/session stats (Cassandra: "Third chicken defeat this week."; Brutus remembers your favourite faction; Plato quotes your longest battle), structured lines with >= 3 slots (`{unit}`, `{unit2}`, `{arena}`, `{streak}`, `{lifetimeStat}`) so 90 templates yield ~400 distinct sentences, a hard target of >= 160 templates, and the repetition test (H2) horizon extended to 60 simulated minutes with a per-line frequency histogram.

**R2-9. The comedy has no independent editor.**
Pill: The rubric (humor.md §7) is applied by the writer. F2-9 volume makes that a rubber stamp; round-1 Q62 asked for an editorial process, v2 gave a checklist.
Demand: a separate COMEDY-EDITOR agent that never saw the writer's context: scores all lines 1-5 blind on the four rubric questions, deletes the bottom 30%, flags the top 10 for placement, runs the sensitivity sweep, and records the cuts in `docs/humor_edit_log.md`. H6 must cite that log, not the author's claim.

**R2-10. First 90 seconds: hints, not a lesson.**
Pill: UI5 verifies two clicks to a battle; it does not verify that a new player understands anything. Mission 1 ("Marathon (Sort Of)") is an ordinary eliminate battle.
Demand: scripted teaching beats in mission 1 (place a spear line, fight, use a god power, see a counter pay off) with a skip; Quick Fight's default armies always include one gag unit and one counter pair so the first battle shows a mechanic and a joke; a persona run (R2-14) must reach "first deliberate counter-pick" within 3 minutes.

**R2-11. Replay value beyond campaign and survival.**
Pill: Sandbox, 9 missions, survival and editors are all "make your own fun" or one-time content; there is no reason to open the game on day 3.
Demand: a **Daily Skirmish** (seed from the local date, fixed budget/arena/enemy style, local result history, copyable result string) and **12 Puzzle Challenges** built on the mission schema ("beat 20 hoplites with 600 drachmae of archers", "hold the pass with only philosophers"). Both reuse armygen and objectives; both are deterministic, so they need no content pipeline beyond data.

**R2-12. No progression pull and no mutators.**
Pill: Campaign rewards are titles and silly cosmetic parts; sandbox is fully unlocked (spec world.md §6). Stars buy nothing a player feels in battles.
Demand: unlockable **rule mutators** earned by campaign stars (>= 8: Big Heads, Tiny Titans, Moon Gravity (knockback x3), Chicken Rain, Wine Rain Always, Friendly Fire Fiesta, Speedy Soldiers, Ragdoll Frenzy), each a data-only rules multiplier on existing systems, shown in the setup rules tablet and tracked by achievements. Cheap, shareable, and the genre's proven replay driver.

**R2-13. The first and last ten seconds of a battle are not designed.**
Pill: Round-1 handled mid-battle juice. The countdown, army "stand-off" beat, the finish and the results hand-off are where a studio game feels finished; spec has only `battle_countdown` and a results banner.
Demand: a 10-second choreography per end state in spec/ui.md: pre-battle (armies idle, banners, crowd, Brutus intro, camera establishing shot), finish (winners `cheer`, losers `rout/sit`, slow-mo on the last kill, Zeus/crowd reaction, jingle ducking), results (camera orbit over the field, stats tablet slide, MVP spotlight). Each with a clip, cue and reduce-motion variant, and a filmstrip in A10.

**R2-14. Persona playtests exist in neither plan nor verification.**
Pill: Round-1 Q60 asked for human-persona notes per mission; verification.md W6 uses scripted bots only, and no row ever asks a novice to try the game.
Demand: at T1a, T1b and T3 an agent persona (novice, picky art director, speed-runner) plays only from screenshots + DOM + `__vw` (no source access), logs every hesitation, dead button, unreadable HUD item and unfunny line with a timestamp; the log is a deliverable (`docs/persona_notes.md`) and each finding becomes a criterion or a fix. Add rows P-novice-1..5 to verification.md.

**R2-15. Cross-device saves are lost silently.**
Pill: Plan §Editors drops `db` ("localStorage -> `db`-less memory fallback") without a stated reason; the user's custom soldiers, arenas and 27 stars live in one browser. A republish to the same URL keeps them; a different device or a cleared browser does not.
Demand: either a written decision in plan.md ("device-local by design, with Export all as backup, shown in Settings > Data") or a `db` mirror for signed-in viewers under the private per-user path with conflict rule "newest wins per doc". Test with storage blocked and `db` null.

**R2-16. Tests are not tested.**
Pill: M1 is not an isolated case: a rule written as "tests run without the autoplay flag" passes on a build with no gesture gate. Verification.md has ~200 rows and no row asks whether the check can fail.
Demand: every `N/B/M` criterion declares a negative control (a mutation or fixture the check must fail on); the QA agent runs the controls at each gate (remove the gesture gate; break the CRC; pop a tint voxel; widen a unit past radius 0.7; drop a cue) and records pass-then-fail evidence. Criteria without a possible failure are `H`.

**R2-17. Cut order is unwritten.**
Pill: Round-1 Q1 asked "which 70%?"; v2 answers with tiers but not an order inside them, and F2-5 shows T1 is too large.
Demand: a ranked cut ladder with triggers in plan.md (e.g. after T1a: drop in order Daily/Puzzles, Achievements 24 -> 16, Mythic 7 -> 4, arenas 14 -> 10, Survival bosses, Codex props tab; after T2: arena-builder symmetry modes, painter onion skin), with the honest-roadmap wording for each cut so the final message can name what was dropped.

**R2-18. The hosted page's real constraints are known only from prose.**
Pill: Plan §0 and spec rely on the Artifact contract text: relative `fetch` of published files, Web Workers from blob, pointer lock from a click, sound after interaction, no query string, `window.open` unreliable, `<title>` name rules, side gutter 16 px and safe-area padding in a skeleton the page does not control. None has a test or a fallback listed.
Demand: a one-page "platform contract table" in spec.md (each assumption, source line, fallback, which criterion tests it), including: credits links as real `<a href target=_blank>`, no reliance on `location.search`, fullscreen/pointer-lock rejection handling, the skeleton's 14 px/off-white defaults overridden by explicit tokens, and a T0 publish rehearsal that pushes >= 300 asset files in batches to measure the real publish and fetch path before the audio pipeline is finished.
